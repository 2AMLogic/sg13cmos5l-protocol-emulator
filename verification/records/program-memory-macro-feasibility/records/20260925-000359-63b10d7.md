- **Record ID**: 20260925-000359-63b10d7
- **Claim**: issue #39 asks a decision record to choose between (1) an SRAM
  macro, (2) an area-budget revision, and (3) a program-size reduction, on
  the premise that the flip-flop 256×16 program memory "cannot fit **any**
  legal Tiny Tapeout tile allocation." This record supplies the two
  measured inputs that decision needs, and **falsifies half of that
  premise**:
  1. **An SRAM macro implementing DR 0001's ratified 256×16 program memory
     exists in this PDK and fits inside the ratified ≤2×2 budget.**
     `RM_IHPSG13_1P_256x16_c2_bm_bist` — 256 words × 16 bits, single-port —
     is **236.8 × 118.78 µm = 28,127.104 µm²**, which is **22.2 %** of the
     2×2 core area, and it fits a 2×2 core box in either orientation. Every
     one of the 27 layer/datatype pairs in its GDS passes the competition
     precheck's own CMOS5L layer allowlist.
  2. **The tile-area constant every prior comparison in this repo used is
     wrong for this shuttle.** Those comparisons used `1 tile ≈ 167 × 108
     µm` — correctly labelled an order of magnitude by both the template
     comment it came from and record `20260922-012402-420c370`. The flow of
     record does not use it: `tt-support-tools`'
     `Project.create_user_config()` sets LibreLane's `DIE_AREA` from
     `tech/ihp-sg13cmos5l/tile_sizes.yaml`, where **1×1 = 202.08 × 154.98
     µm, 2×2 = 419.52 × 313.74 µm, 8×4 = 1724.16 × 710.64 µm**. Against
     those, the flip-flop memory **still cannot fit the ratified ≤2×2
     budget** (2.46×–2.98× the whole 2×2 core area in cell area alone,
     per flow) — but it is **not** over the 8×4 competition maximum: it
     lands at **25.8 % (klt flow) / 31.3 % (LibreLane flow)** core density
     at 8×4. The "1.36× over even the 8×4 maximum" figure in record
     `20260922-012402-420c370` is an artifact of the superseded constant.
     That record is **not edited** (append-only); this one is the later
     record that says why, per `CLAUDE.md`.

- **Result**: **MEASURED — the macro option is open, and the "no legal tile
  allocation fits" premise is half false.**
  - **SRAM library present.** `libs.ref/sg13cmos5l_sram` resolves. It is a
    **symlink** (`-> ../../ihp-sg13g2/libs.ref/sg13g2_sram`; git tree mode
    `120000` at the PDK revision the flow of record installs,
    `2bbec755dc67…`) — i.e. IHP ships **one** SRAM macro set shared by
    SG13G2 and CMOS5L, rather than a CMOS5L-specific one. This resolves in
    CI because `tt-gds-action@ihp-cmos5l`'s `install_sg13cmos5l.sh` checks
    out the **whole** IHP-Open-PDK tree, not just the CMOS5L subtree. **Open
    item, stated rather than assumed:** whether IHP/Tiny Tapeout qualify
    these macros for the CMOS5L shuttle is a question for the shuttle
    organisers; this record establishes availability and geometric/precheck
    compatibility, not shuttle admission.
  - **Exact-size macro exists.** `RM_IHPSG13_1P_256x16_c2_bm_bist`:
    LEF `SIZE 236.8 BY 118.78` → **28,127.104 µm²**; liberty `area :
    28127.104`; drawn bbox from `klt stats` 236.8 × 119.005 µm (a 0.225 µm
    bottom overhang beyond the LEF abstract — noted for the floorplan, not
    a blocker). Single-port, **one-cycle data access** (synchronous read:
    address registered on the rising edge, data valid the following cycle);
    `A_CLK → A_DOUT` worst-case **5.0 ns at `slow_1p08V_125C`**, i.e. 25 %
    of a 20 ns (50 MHz) period. 1P/2P family footprints for every shipped
    depth × width are in the artifacts.
  - **Competition precheck layer check: PASS, mechanically.** All **27**
    layer/datatype pairs used by the macro GDS are on
    `valid_layers_ihp_sg13cmos5l`; **zero** excess layers. Top routing layer
    is **Metal4** — exactly `tt-support-tools`' `project_top_metal_layer`
    for CMOS5L, and inside the CMOS5L stack (which has no Metal5/TopMetal2).
    The allowlist explicitly carries `SRAM.drawing` (25/0) and
    `DigiBnd.drawing` (16/0), both of which the macro uses: **the
    competition's own precheck already anticipates an SRAM bit-cell marker
    inside a CMOS5L user project.** Cell names carry no `#` or `/`
    (`cell_name_check`).
  - **The core-area model is validated against the flow of record itself.**
    At `tiles: "1x1"` the model gives a core box of 196.32 × 147.42 µm =
    28,941.4944 µm²; LibreLane's own reported standard-cell area for the
    full design on PR #38's `gds` run implies a core density of
    **1306.3142 %**, against the **1306.314 %** OpenROAD reported in
    `GPL-0301`. Agreement to 7 significant figures — the arithmetic below is
    LibreLane's arithmetic, not an approximation of it.

  - **What this changes, stated plainly:** the flip-flop memory's non-fit
    against the **ratified ≤2×2 budget** stands and is if anything
    unambiguous (it needs 2.46×–2.98× the entire 2×2 core area in cell area
    alone, so no utilization setting rescues it). Its claimed non-fit
    against the **8×4 competition maximum** does not stand: at the correct
    die areas the flip-flop memory would fit an 8×4 — and a 5×4 — with the
    core. And the SRAM macro makes the *ratified* budget reachable rather
    than merely reducing the overage.
  - **What this record does NOT establish** (deliberately, so nothing here
    is over-read): that a macro-based design closes timing, routes, passes
    DRC/LVS, or that LibreLane's macro flow (`MACROS` / `EXTRA_LEFS` /
    `EXTRA_LIBS` / `EXTRA_GDS_FILES` / `PDN_MACRO_CONNECTIONS`, plus the
    macro's third supply pin `VDDARRAY!`) is configured correctly under
    Tiny Tapeout's `src/config.json` merge. Those are the implementation
    issue's first acceptance criteria, named in
    `spec/decision-records/0005-program-memory-implementation.md`.
