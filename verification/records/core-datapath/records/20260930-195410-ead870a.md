  - **13/13 directed cases passed** (0 failed, 0 skipped; per-test statuses in
    `artifacts/20260930-195410-ead870a/results_icarus.xml`). Every program is loaded

    ISA has no instruction that reads C, so C is not pin-observable at all in this
    revision).
  - **Coverage of the opcode table**: all 16 opcodes execute as loaded firmware —
    `NOP` (`test_nop_costs_one_cycle`), `LDI`/`MOV`/`OUT` (`test_ldi_mov_out_write_latency`),
    `ADD`/`SUB`/`AND`/`OR`/`XOR` (`test_alu_results_pin_observable`, both operand
    shapes), `SHF` both directions (`test_shf_results_pin_observable`), `IN` on both
    readable ports plus both direction no-ops (`test_in_ports_and_direction_noops`),
    `OUT` to port 11 (`test_out_port11_drives_uio_out_not_oe`), `WAIT` at three
    immediates including the `WAIT 0` corner (`test_wait_cycle_exact`), `JMP`, `BZ`
    taken and `BNZ` not-taken (`test_branches_taken_and_not_taken`), `BNZ` taken in a
    loop (`test_bnz_taken_countdown_loop`), and `HALT` freezing the core (checked in
    four separate tests).
  - **Cycle-exactness, which is the point of the ISA**: every assertion is on a
    *numbered rising edge* counted from the MODE-drop edge, derived from DR 0001's own
    per-instruction cycle table (`cycles()` / `retire_edge()` in the bench) and not
    from observing the RTL. Specifically pinned: a 1-cycle instruction at program
    index *i* retires at edge *i* + 2; `WAIT imm8` consumes exactly imm8 + 1 slots (5,
    1 and 2 checked); a taken `BZ`, a taken `BNZ`, an untaken `BNZ` and a `JMP` each
    cost exactly 1 cycle with no bubble; the DR 0001 compile-time-constant countdown
    loop (`OUT`/`SUB`/`BNZ`) runs at **exactly 3 cycles per iteration** for three
    iterations, which is the loop shape the UART low-baud cycle budget is written in;
    and an `OUT`'s value reaches the pin exactly one cycle after the `OUT` executes
    and **not the cycle before** (each `OUT` test asserts the negative as well as the
    positive).
  - **DR 0005's fetch-ahead amendment is verified, not assumed.**
    `test_run_entry_fetch_ahead_costs_exactly_one_cycle` pins the one spec-visible
    consequence — run-phase entry costs a **fixed +1 cycle, and exactly one**: the
    first run-phase cycle presents address 0 and executes nothing, the instruction at
    address 0 executes in the second. The test asserts `uo_out == 0x00` at edge 2 (a
    regression to the superseded same-cycle-fetch model would already show the marker
    there) and `0xA5` at edge 3 (a two-cycle or bubbled entry would miss it), so it
    fails in both directions. Every other cycle-exact test above then *re-confirms*
    the zero-extra-cost half of the amendment: the loop, branch and WAIT arithmetic
    would all shift if any instruction had picked up a fetch bubble.
  - **`test_latency_independent_of_data`** runs the same instruction sequence twice
    with ALU data differing in every flag-relevant way (one `ADD` yielding 0x00 with
    Z=1, C=1; the other 0xF9 with Z=0, C=0) and requires the trailing marker on the
    *same* retirement edge both times — the bench-level shadow of
    `spec/verification-plan.md` §2.1's `no_data_dependent_latency` property. It is a
    bench, not the formal property: §2.1's own qualification run
    (`verification/records/no-data-dependent-latency/`) is still against a fixture,
    and re-running it byte-identically against **this** core is issue #24's remaining
    scope, not claimed here.
  - **Template `test/` harness: PASS, 1/1** (`test.test_project`, 1,710,001 ns
