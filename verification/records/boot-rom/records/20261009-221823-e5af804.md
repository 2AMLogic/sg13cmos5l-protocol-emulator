- **Record ID**: 20261009-221823-e5af804
- **Claim**: DR 0013 layer 2's infrastructure (`spec/decision-records/0013-program-loading.md`, **Proposed, not ratified**), as issue #138 scopes it, holds on the RTL of the submitted top, and with it target-spec row 14 (c) for the RTL: **with `MODE` low at `rst_n` release the core runs the boot ROM, drives no pin, and never decodes program memory unless a boot program has verified the image in it.** Specifically: (a) straps `00`, `01` and `11` (the UART-load and SPI-flash stubs, and the reserved value) on a program memory that has never been written leave `uo_out`, `uio_out` and `uio_oe` at 0 and free of X, in reset and after it; (b) with program memory holding a canary image that is shown to drive `uo_out` and every `uio` enable when it runs, or any of four random images, a `MODE`-low reset moves no pin on any of the four strap values, including strap `10`, whose check fails on all five; (c) strap `10` (warm start) runs an image whose word 255 is the CRC-16/XMODEM of words 0-254 (`binascii.crc_hqx`), from address 0, with its first instruction executing exactly 2,323 cycles after the boot program's first, with `R0`-`R3`, `Z` and `C` at their reset values, `PM_ADDR` and `PM_CRC` reading 0 and `BOOT_STATUS` reading `0x00`, and leaves the array intact (a second warm start passes); two images with different contents move their pins on identical edges; (d) seven images one defect away from a verified one are never run; (e) a serial load is unaffected and reads `BOOT_STATUS = 0x01`; (f) the committed chain holds: `boot_rom.asm` assembles to `boot_rom.hex` (30 words, cap 128), and `rtl/protocol_boot_rom.v` is what the generator makes of that image. White-box, RTL only: the fetch-source flag is 1 from reset until the `RUN`'s stall cycle ends and 0 after it; while it is 1 the core requests no program-memory fetch and the macro's read enable is high only for the warm start's 256 data reads; the stubs halt at the addresses the strap table names; a failed warm start halts in the UART-load stub. **Finding F1, recorded and pinned, not fixed:** the all-zero image passes the warm-start check, because CRC-16/XMODEM starts at `0x0000` and the CRC of zeros is zero. A warm start runs it. It is 256 `NOP`s and no pin moves (`test_warm_start_all_zero_image_is_the_known_weak_case`). Row 14 (c)'s wording, "never executes program memory whose contents were not loaded and integrity-checked", is therefore met by this design for every image the bench tried except that one, for which the check passes by arithmetic; see DR 0013's implementation notes. **Not claimed:** (1) rows 14 (a) and (b) -- the random-initial-state and X-propagation gate-level regression and the reset-coverage listing of `spec/verification-plan.md` section 8 are not built; this bench starts every case from `rst_n` with RTL flops, and its "random" memory is random *contents* written through the serial loader before a `MODE`-low reset, not a randomized power-up. (2) The UART and SPI-flash boot programs (issues #139, #140): the stubs are a `HALT` each. (3) Anything on a gate-level netlist: that is `verification/records/firmware-gate-level/` at this commit. (4) A clock frequency, an area or a pad. (5) A warm start on a never-written (X) memory: the stub straps never read the array and are exercised on X; the warm start reads every word, and is exercised on real contents only (the bench's docstring says why).

- **Statistical convention**: Directed tests. Random program-memory images and filler come from `random.Random` with literal seeds in the source (`0x138` for the four random images, 1, 2 and 3 for the signed images' filler); the request's `random_seed: 1` is recorded and unused. Every run is byte-reproducible. The image sets are small (five unverified images, two verified, seven corrupted): this is a directed check of the mechanism, not a statistical claim about CRC escape rates, which for a 16-bit CRC is 1 in 65,536 for a random image by construction.
- **Result**: **PASS, 6/6**: `test_boot_image_chain_and_model`, `test_stub_straps_idle_on_unwritten_memory` (2,581 ns), `test_mode_low_never_runs_unverified_memory` (338,651 ns), `test_warm_start_runs_a_verified_image` (184,161 ns), `test_warm_start_rejects_corrupted_images` (455,071 ns), `test_warm_start_all_zero_image_is_the_known_weak_case` (72,101 ns). **Where the expected numbers come from.** The bench carries `BootModel`, an interpreter of the ISA written from DR 0001's opcode table and DR 0012's register map and latency table, sharing no code with the RTL or the assembler. It runs the committed boot image against a strap value and a memory image and says where the boot program ends and after how many cycles; every asserted edge comes from it. It reproduces the 2,323-cycle figure the boot source documents (6 for the dispatch, 4 to set up, 256 x 9 for the loop, 4 for the verdict, 3 to restore state, 2 for `RUN`), it reports 256 data reads and 256 commits for a warm start with the array unchanged, and zero of each for a stub. **Corrupted images, none run:** one flipped bit in word 0, in word 127, in word 254 and in the signature word; words 100 and 101 swapped; and two images crafted so that exactly one byte of the CRC residue is zero, which a check comparing half of `PM_CRC` would pass. **Negative controls: 10 of 10 caught, each by a test meant to catch it**, after a copy of the unmodified sources passes 6/6: `rom-never-selected` (4 of 6 fail); `run-does-not-leave-rom` (2 of 6 fail); `run-target-not-fetched-from-memory` (2 of 6 fail); `boot-status-bit1-stuck` (1 of 6 fail); `macro-read-not-gated` (5 of 6 fail); `warm-start-skips-verdict` (3 of 6 fail); `verdict-ignores-crc-high-byte` (2 of 6 fail); `verdict-ignores-crc-low-byte` (2 of 6 fail); `straps-01-and-10-swapped` (6 of 6 fail); `handover-leaves-z-set` (2 of 6 fail). Four are defects in the RTL (the fetch source never selecting the ROM, `RUN` not leaving it, `RUN`'s target not fetched from memory, `BOOT_STATUS[1]` stuck), one in the program memory (the macro read for fetch during boot, invisible at the pins and caught by the white-box read-enable check), and five in the boot program, injected as a changed word in the copy of the generated ROM (the verdict branch removed, the verdict testing one CRC byte only, in each direction, the two strap values swapped, and `Z` not restored at handover). A ROM mutant also fails `test_boot_image_chain_and_model` by construction; that failure is not counted, and each ROM mutant fails at least one behavioural test as well.
