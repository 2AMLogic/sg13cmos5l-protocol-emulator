- **Record ID**: 20261010-020820-0f0490a
- **Claim**: DR 0013 layer 2's infrastructure (`spec/decision-records/0013-program-loading.md`, **Proposed, not ratified**), as issues #138 and #140 scope it, holds on the RTL of the submitted top, and with it target-spec row 14 (c) for the RTL: **with `MODE` low at `rst_n` release the core runs the boot ROM, and never decodes program memory unless a boot program has verified the image in it.** Specifically: (a) straps `00` and `11` (the UART-load stub and the reserved value) on a program memory that has never been written leave `uo_out`, `uio_out` and `uio_oe` at 0 and free of X, in reset and after it; (b) with program memory holding a canary image that is shown to drive `uo_out` and every `uio` enable when it runs, or any of four random images, a `MODE`-low reset moves no pin on strap values `00`, `10` and `11`, including strap `10`, whose check fails on all five; (c) strap `10` (warm start) runs an image whose word 255 is the CRC-16/XMODEM of words 0-254 (`binascii.crc_hqx`), from address 0, with its first instruction executing exactly 2,323 cycles after the boot program's first, with `R0`-`R3`, `Z` and `C` at their reset values, `PM_ADDR` and `PM_CRC` reading 0 and `BOOT_STATUS` reading `0x00`, and leaves the array intact (a second warm start passes); two images with different contents move their pins on identical edges; (d) seven images one defect away from a verified one are never run; (e) a serial load is unaffected and reads `BOOT_STATUS = 0x01`; (f) the committed chain holds: `boot_rom.asm` assembles to `boot_rom.hex` (93 words, cap 128), and `rtl/protocol_boot_rom.v` is what the generator makes of that image. White-box, RTL only: the fetch-source flag is 1 from reset until the `RUN`'s stall cycle ends and 0 after it; while it is 1 the core requests no program-memory fetch and the macro's read enable is high only for the warm start's 256 data reads; the stubs halt at the addresses the strap table names; a failed warm start halts in the UART-load stub. **Finding F1, recorded and pinned, not fixed:** the all-zero image passes the warm-start check, because CRC-16/XMODEM starts at `0x0000` and the CRC of zeros is zero. A warm start runs it. It is 256 `NOP`s and no pin moves (`test_warm_start_all_zero_image_is_the_known_weak_case`); see DR 0013's implementation notes. **What changed with issue #140:** strap `01` is no longer a stub. It is the SPI-flash boot, which drives the flash pins (CS0, MOSI, SCK) by design, so it is no longer part of this bench's "no pin moves" properties (a), (b) and (c)'s stub loop; its properties are `verification/records/boot-spi/`'s. The ROM grew from 30 to 93 words and the warm start's code moved one address down (its stub neighbour is gone), so this bench's negative controls address the moved words; the warm start's cycle count, 2,323, is unchanged. **Not claimed:** (1) rows 14 (a) and (b) -- the random-initial-state and X-propagation gate-level regression and the reset-coverage listing of `spec/verification-plan.md` section 8 are not built; this bench starts every case from `rst_n` with RTL flops, and its "random" memory is random *contents* written through the serial loader before a `MODE`-low reset, not a randomized power-up. (2) The UART-load boot program (issue #139): its stub is a `HALT`. (3) Anything on a gate-level netlist: that is `verification/records/firmware-gate-level/` at this commit. (4) A clock frequency, an area or a pad. (5) A warm start on a never-written (X) memory: the stub straps never read the array and are exercised on X; the warm start reads every word, and is exercised on real contents only (the bench's docstring says why). **Why this record exists.** Issue #140 changed hashed inputs of `20261010-004726-197191d` (the boot ROM and its source, image and cycle report, `verification/test_boot_rom.py` and `verification/boot_rom_mutants.py`), so that record went stale; per the append-only rule it is left untouched, and this record re-runs the bench and its negative controls on the tree at `0f0490a` and supersedes it.
