- **Record ID**: 20261009-215352-ce64319
- **Claim**: The RTL implements the load-integrity readout of DR 0013 layer 1 (`spec/decision-records/0013-program-loading.md`, **Proposed, not ratified**; issue #137), and this is `spec/verification-plan.md` section 7's "Load integrity" check for it. Observed at the pins, RTL simulation: (a) while the design is in load phase, `uo_out` is the running `PM_CRC`, its low byte when `ui_in[1]` = 0 and its high byte when `ui_in[1]` = 1, and for random images of 1, 2, 3, 16, 97 and 256 words that value equals `binascii.crc_hqx(image_bytes, 0)` (Python's standard library; image as big-endian bytes, word 0 first); (b) it is the *running* CRC: after each committed word it equals the CRC of the words so far, and it does not move on the 15 edges between commits; (c) the byte select is `ui_in[1]` alone, takes effect without a clock edge, and no other `ui_in` or `uio_in` pin changes what is read; (d) a truncated load, a load with one clock edge dropped and a load with one clock edge doubled read a CRC different from the image's whenever memory ends up holding something other than the image, and in every such case the readout equals the CRC of what was really committed, computed independently bit by bit; (e) the load protocol is unchanged: a host that performs the readout, with the clock stopped or still running, gets the program executing on the same edges as a host that does not, and `BOOT_STATUS[0]` reads 1; (f) outside the load phase there is no readout: `uo_out` is 0 while reset is held and on the mode-sampling cycle, and from the `MODE`-drop edge it is the core's register, which neither `ui_in[1]` nor a re-raised `MODE` reaches; (g) after 256 words the readout stops moving. **What this record does not claim.** Not a proof for every image: (d) is a set of asserted facts about the seeded images below. A 16-bit CRC passes about one corrupted load in 65,536. Nothing at gate level (that is `verification/records/firmware-gate-level/` at this commit), nothing about timing of the `ui_in[1]`-to-`uo_out` path (the LibreLane record at this commit carries the flow's timing), nothing about pads, and nothing about DR 0013's layers 2 and 3 (the boot ROM is issue #138, `loadseq` is issue #118). **Findings, recorded and not acted on** (also written into DR 0013's findings section): **F1** `uo_out` during a serial load is not its reset value, which conflicts with target-spec row 14(b) as worded, and peers wired to `uo_out` (UART TX on `uo_out[0]`, SPI CS/SCLK/MOSI on `uo_out[0..2]`) see CRC bits during a load. **F2** The CRC starts at `0x0000`, so an all-zero image reads `0x0000` at any length, including when no clock edge arrived at all; no fault of such an image is detectable. **F3** One doubled edge is undetectable because it is harmless: a repeat of a bit in a run of equal bits that reaches the end of the image leaves every word intact, and the readout correctly matches. **F4** DR 0010's pin table still lists `ui_in[1]` and `uo_out` with `load_role: none`.
