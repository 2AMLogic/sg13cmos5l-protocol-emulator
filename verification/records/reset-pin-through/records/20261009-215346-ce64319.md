- **Record ID**: 20261009-215346-ce64319
- **Claim**: The reset/pin contract this experiment carries, **narrowed by one clause because issue #137 changes it.** Still true, and re-run here: after `rst_n` both pin-output *registers* read 0 and `uio_oe` reads 0; the load phase changes neither register and leaves `uio_out` and `uio_oe` at 0; and at the first point this bench reads the pins -- just after the `MODE`-drop edge -- `uo_out`, `uio_out` and `uio_oe` are all 0 and stay 0 through a `HALT`. **Withdrawn and replaced:** `20261009-201346-4ff0e14` says of the pins that "the load phase changes neither". For the `uo_out` *pin* that is no longer so. Since commit `ce64319` (DR 0013 layer 1) `uo_out` shows the running `PM_CRC` from the mode-sampling edge until the `MODE`-drop edge: 0 until the first word commits, then CRC bytes. The register behind it (`port_uo_out`) is still 0 throughout, and `uo_out` is 0 whenever reset is held. This bench cannot see the difference, because its loader returns after the `MODE`-drop edge; what `uo_out` does before that edge, in reset and on the mode-sampling cycle is checked edge by edge in `verification/records/load-integrity/` (`test_no_readout_outside_the_load_phase`, `test_load_protocol_unchanged_by_the_readout`). The superseded record's account of why `uio_oe` is 0 after reset (DR 0012's reset values) stands as written. **Target-spec row 14(b)** says `uo_out` "holds its documented reset value until a program writes" it; the readout is an exception to that wording, recorded as a finding in DR 0013, not resolved here.
