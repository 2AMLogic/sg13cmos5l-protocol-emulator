- **Record ID**: 20261009-221801-e5af804
- **Claim**: The reset/pin contract of `20261009-201346-4ff0e14` still holds with the boot ROM in the design: **after `rst_n`, both pin-output registers read 0 and `uio_oe` reads 0, and the load phase changes neither.** This bench reaches that state with `MODE` high (a serial load). The other way out of reset, `MODE` low, used to run program memory and now runs the boot ROM; what the pins do there is a different experiment, `verification/records/boot-rom/`, which checks that no pin moves on any strap value unless a verified image is warm-started. `verification/_dut.py`'s unused `reset()` helper, which this experiment hashes, gained a docstring paragraph saying so and no code. **Why this record exists.** Issue #138 implements DR 0013 layer 2 (`spec/decision-records/0013-program-loading.md`, Proposed): with `MODE` low at `rst_n` release the core now fetches from an on-chip boot ROM (`rtl/protocol_boot_rom.v`) and decodes program memory only after a boot program's `WCTL RUN`. Commit `1dc1842` changed `rtl/protocol_core.v` (a second instruction input and the fetch-source flag), `rtl/protocol_program_memory.v` (the macro is not read for fetch while the ROM is the source) and the top (the ROM instance). `20261009-201346-4ff0e14`'s `provenance.inputs` hash all three, so that record went stale; per the append-only rule it is left untouched, and this record re-runs the same thing on the new RTL and supersedes it. Every case in this bench enters the run phase through a serial load (`MODE` high), the path DR 0013 leaves "unchanged, pin for pin and cycle for cycle", and never decodes a ROM word; the boot ROM's own evidence is `verification/records/boot-rom/`.
