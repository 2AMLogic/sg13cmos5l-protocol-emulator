- **Claim**: like its sibling at this record ID under `sta-corner-sweep/`, this is a
  **negative** result, recorded rather than left as a stale number. The klt-flow
  place-and-route die-area leg **cannot run** against the macro-backed ISA core:
  `klt place-and-route`'s request schema has no field for a hard macro's LEF, so
  OpenROAD aborts at the `floorplan` stage before any floorplan exists. DR 0005's
  open item 2 asks the implementation issue for "a measured die area for the
  macro-backed design, **on both flows**"; this record supplies the klt flow's half
  as an explicit **not obtainable at this toolchain pin**, with the reason, rather
  than silently leaving the superseded flip-flop-era die area in force.

- **Result**: **FAIL / BLOCKED — neither top reached a floorplan.** Both
  `klt place-and-route` invocations failed identically:

  ```
  openroad 'floorplan' stage failed: [ERROR ORD-2013] instance u_prog_mem/u_sram
  LEF master RM_IHPSG13_1P_256x16_c2_bm_bist not found.
  ```

  (and the same for `u_sram` in the stand-alone program-memory top). No die area, no
  core area, no placed utilization was produced, and none is claimed.
  - **Tool gap, filed**: `klt.place_and_route.request/1` has no `macros` /
    `extra_lefs` entry, so the macro's abstract is never read — and beyond reading
    it, the request also has nowhere to put the three other things a macro-bearing
    floorplan needs: a fixed **placement** per macro instance, a **halo**, and the
    macro **GDS** for stream-out. **2AMLogic/klayout-tools#2635** asks for one shared
    `macros` block across `synthesize`/`sta`/`place-and-route` covering exactly
    those. This is DR 0005's **open item 4** landing as predicted; it is the first
    time this repo's iteration flow has tried to place a hard macro against this PDK,
    which is what open item 4 said would be the test.
  - **The klt flow's own standing gaps are unchanged and still relevant**: even with
    the macro read, `sg13cmos5l_stdcell` has no verified CTS-buffer /
    routing-layer-range / antenna-diode entries at this pin, so this flow has never
    got past `stage_reached: place` for this library anyway (recorded in
    `20260922-012402-420c370` and unchanged since).
  - **Where the area answer actually comes from now.** The LibreLane flow of record
    is the one that can place this design — `src/config.json` carries the macro's
    LEF/liberty/GDS and a fixed placement for it, and `info.yaml` declares
    `tiles: "2x2"` — so the **`gds` workflow run on this branch is the measurement**,
    and per `CLAUDE.md`'s two-flows rule it is reported as LibreLane's, not as a
    substitute for the klt number this record could not produce. The supporting
    arithmetic (cells 10,323.2556 µm² + macro 28,127.104 µm² = 38,450.36 µm² =
    30.35 % of the 2×2 core's 126,685.0368 µm²) is in the synthesis-baseline record
    at this ID and is **arithmetic, not a placement**.
  - **What the superseded records said, preserved and not contradicted.**
    `20260922-012402-420c370` measured the flip-flop program memory at die
    787,434 µm² / 312,062.8896 µm² of cells, and `20260925-000359-63b10d7` corrected
    the tile constant those comparisons rested on. Both stand as measurements of the
