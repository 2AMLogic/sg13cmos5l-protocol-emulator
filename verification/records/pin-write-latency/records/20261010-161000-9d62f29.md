- **Record ID**: 20261010-161000-9d62f29
- **Claim**: The formal property `pin_write_latency` (spec/verification-plan.md section 2.2) **holds on the shipped core `rtl/protocol_core.v` with DR 0015's P1 and P2 built in (issue #208), with one stated abstraction for the new readable registers**: every executed `OUT` to port 10 or 11 writes at the edge that retires it, the other port holds, and nothing else moves an output. ABC `scorr` + `pdr` proved every assertion in both clock models, unbounded for the harness model, and the same fifteen mutants are still rejected. **What the abstraction is, and why it is disclosed here rather than buried.** The CRC and line units live inside the core, so unlike `PM_CRC` they cannot be a free input the monitor shares, and the monitor's shadow of the ISA does not re-implement them. The shadow therefore marks a register that was loaded by an `RCTL` of a P1/P2 readable index (`CRC_CFG`, `CRC_POLY`, `CRC_STATE`, `CRC_NEXT`, `LINE_CFG`, `LINE_OUT`, `LINE_STUF`), or computed from one, or stored through `UIO_DIR` / `UIO_OD` / `PM_ADDR` and read back, as "value not modelled". For an `OUT` of such a register the property still checks **when** the pin changes (only on the edge retiring an `OUT` to that port) and **where** (the right port, the other port holds), but **the equality of the pin value to the shadow's value is waived for that write**. Every value not derived from a P1/P2 read is checked exactly as before. So for P1/P2-derived values this property is weaker than it was, and the values are instead graded by `verification/records/primitives/` (independent oracles) and `verification/records/isa-lockstep/` (the ISA model, extended). `WCTL CRC_BYTE` is modelled for timing as a `WAIT 8`. **Limits, unchanged in kind from the superseded record:** unbounded for the harness model only (two 8-word aliased tables, a clock-synchronised reset, zero-delay RTL); a program-memory write does not change the constant tables; and this property says what each fetched instruction does to the pins, not which instruction is fetched next (`no_data_dependent_latency`). **Why this record exists (issue #208):** the core changed, and the monitor (the abstraction above) and the runner's inputs changed with it, so the superseded record's hashes went stale. Nothing in it is corrected.
