- **Record ID**: 20261009-214736-1dc1842
- **Claim**: The formal property `pin_write_latency` (spec/verification-plan.md section 2.2) still **holds on the shipped core `rtl/protocol_core.v`** now that the core has two instruction sources -- the boot ROM of DR 0013 layer 2 and program memory -- and a fetch-source mux between them: every executed `OUT` to port 10 or 11 writes the source register's pre-edge value at the edge that retires it, the other port holds, and nothing else moves an output, **whichever source each instruction was fetched from and across the switch from one to the other**. ABC `scorr` + `pdr` proved every assertion in both clock models, unbounded for the harness model. **What changed, and why this is more than a hash refresh.** (1) *The harness.* Its run phase used to mean "`MODE` low, run program memory", with one free 8-word program table. That is no longer what the design does. The harness now has two free tables, `prog*` (program memory) and `rom*` (the boot ROM), each behind its own registered read port, so the result quantifies over every ROM image as well as every program, not over the one committed boot image. (2) *The monitor.* Its shadow of the ISA would be wrong on this core if left alone: it would execute program-memory words while the core executes ROM words. The shadow now receives both words and selects with its own state, written from DR 0013 and DR 0012 (`RUN`: "switch the fetch source to program memory"): the ROM is the source unless a serial load completed, until a `WCTL RUN` completes. It never reads the core's `fetch_rom` output. `BOOT_STATUS` in the shadow reads `{from_rom, serial_loaded}`, so the bit-1 value the core reports is checked through any `OUT` that carries it to a pin. (3) `serial_loaded` is still a free per-step input here, so the proof also covers the source changing at steps the design cannot produce; that is a superset of the reachable behaviour, and the proof closes on it. **Limits, unchanged in kind from the superseded record:** unbounded for the harness model only (two 8-word aliased tables, a clock-synchronised reset, zero-delay RTL); a program-memory write does not change the constant tables (`verification/records/control-space/` owns that); and this property says what each fetched instruction does to the pins, not which instruction is fetched next (`no_data_dependent_latency`). That the *committed* boot program does what DR 0013 says is `verification/records/boot-rom/`, not this record.
