  **Explaining the 16-vs-32 discrepancy.** LibreLane's `Yosys.Synthesis` step runs a `HILOMAP` pass (mapping constant-value driver nets to dedicated `sg13cmos5l_tielo`/`sg13cmos5l_tiehi` tie-cells) as part of its own synthesis script, immediately after ABC technology-mapping and before its own final `stat` report. The Yosys-standalone leg's pass sequence (`read_verilog` -> `hierarchy -check -top` -> `synth -top` -> `dfflibmap -liberty` -> `abc -liberty` -> `clean` -> `stat -liberty ... -json -top`, see `flow/run_synthesize_direct_yosys.py`) has no equivalent pass -- it never runs `hilomap`, so any constant-driven nets stay as plain RTLIL constants in its netlist rather than being instantiated as physical tie-cells. The stub's `ena`-hold logic (the `$_MUX_`/`sg13cmos5l_mux2_1` cells both records agree on) evidently drives one full-width constant net through the reset path, which HILOMAP instantiates as 16 `sg13cmos5l_tielo` cells (one per bit) inside LibreLane's flow but which the Yosys-standalone leg leaves as an implicit constant. This is a genuine flow-configuration difference (which passes each Yosys invocation runs), not a bug in either leg, an ABC nondeterminism, or a PDK/liberty mismatch -- both legs agree exactly on the substantive logic (8 `sg13cmos5l_dfrbpq_1` register bits, 8 `sg13cmos5l_mux2_1` mux cells); they diverge only on whether constant-tie insertion happens before the cell count is taken. Per `CLAUDE.md`'s "two flows, one record of truth" rule, this is recorded as a finding, not reconciled by omitting either number.
