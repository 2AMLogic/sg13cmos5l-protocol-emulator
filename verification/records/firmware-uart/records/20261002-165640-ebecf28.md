- **Claim**: A **committed** UART program — `firmware/asm/uart_tx.asm`, image
  `firmware/build/uart_tx.hex` — loaded over the real serial load-phase pins
  (`ui_in[7]` = MODE, `ui_in[0]` = data) onto `tt_um_2amlogic_protocol_emulator`
  and executed by `rtl/protocol_core.v` transmits 8N1 UART frames whose
  **bit period is exactly 50 core cycles**, and the **independent** reference
  model `verification/reference_models/uart.py` — which shares no code with this
  repo's RTL or firmware and knows nothing of DR 0001's cycle arithmetic —
  recovers both transmitted bytes from the captured pin waveform and grades the
  measured frame timing inside target-spec row 10's cumulative-drift bound
  (measured drift: **0.000 %** of the bit period on both frames; bound 2.0 %).
  This is issue #71's scope, the UART third of issue #23's three-protocol batch,
  and it is what `CLAUDE.md`'s "firmware is evidence" requires of a protocol
  claim: a committed program, run on the RTL under cocotb, passing against an
  independent reference model of that protocol with the timing checked.

  at one bit rate expressed in cycles, under Icarus. It claims **no clock
  frequency** (see "No baud rate is measured" below), no receive path, no SPI
  and no I2C (the sibling sub-issues of #23), no area, no gate-level or
  post-layout result, and no silicon result. It also does not by itself close

  - **The decode is done by the independent model, not by the bench.** The bench
    captures `uo_out[0]` **after every rising clock edge** (never a coarser poll

    `verification/reference_models/waveform.py` `Signal`, then hands that
    `Signal` to `UartDecoder(1_000_000).decode(...)`. The decoder finds the start
    bits itself, samples the ten nominal bit centres, reassembles the bytes,
    checks the stop bits and *measures* the cumulative actual-vs-nominal frame
    drift; `UartDecoder.check_frame` grades that measurement. The only bench-side
    inputs to the comparison are the two payload bytes the committed program is
    written to send. Decoded:
    `UartFrameReport(data=0x5a, t_start=16360.001ns, stop_ok=True, drift=0.000ns (0.000% of bit))`
    and
    `UartFrameReport(data=0xa5, t_start=30560.001ns, stop_ok=True, drift=-0.000ns (0.000% of bit))`.
  - **Measured bit period: exactly 50 core cycles**, on both frames, at the pin.
    Measured as clock-edge indices, so the number carries no clock-rate
    assumption: frame 0 (`0x5A`) start edge at cycle 263 with intra-frame TX-edge
    intervals `[100, 50, 50, 100, 50, 50, 50]` cycles; frame 1 (`0xA5`) start
    edge at cycle 973 with intervals `[50, 50, 50, 50, 100, 50, 50]`. Every
    interval is a whole multiple of 50, the smallest is exactly 50, and every
    edge sits on the 8N1 grid the framing convention requires for that payload
    (`expected_edge_offsets` in the bench derives the legal offsets from the
    framing convention alone). Frame-to-frame pitch measured **710 cycles**,
    matching static arithmetic over the instruction stream (9 bit periods +
    `OUT` 1 + `WAIT 255` 256 + three `LDI` 3).

  - **ISA finding: DR 0001's UART cycle-budget sketch holds.** The sketch
    (`spec/decision-records/0001-isa.md` § "Per-protocol cycle-budget sketch →
    UART (bit-banged, 8N1)") predicts a 50-cycle bit period at 1,000,000 baud
    from a 4-cycle `MOV`/`AND`/`OUT`/`SHF` body plus `WAIT 45` (46 cycles). That
    arithmetic is **confirmed against the real core** at the total: 50 cycles/bit,
    measured at the pin. One reconciliation is worth recording rather than
    leaving as an unexplained discrepancy in the immediate: this program uses
    DR 0001's own blessed compile-time-constant-trip-count loop (`LDI` count,
    `SUB` + `BNZ` body) instead of eight unrolled copies of the sketch, so two of
    the sketch's 46 padding cycles are spent on `SUB` + `BNZ` and the immediate
    is `WAIT 43` (44 cycles) rather than `WAIT 45`. The per-bit total is
    unchanged. No ISA defect, no assembler gap and no spec change was needed for
    this program: all five mnemonics the sketch names, the `.cyclesec` directive,
    and the 256-word program memory were sufficient as ratified-as-proposed.
  - **`WAIT`'s 256-cycle ceiling is untouched by this program, and that is the
    next UART gap.** 50 cycles/bit fits in a single `WAIT`, so this record covers
    only the fast end of target-spec row 1's 9,600–1,000,000 baud range. DR
    0001's own note — that 9,600 baud needs 5,208 cycles/bit and therefore an
    outer constant-trip-count loop around the inner `WAIT` — is **not** exercised
    here and remains unmeasured. The low-baud loop shape itself is independently
    measured (the 3-cycle `OUT`/`SUB`/`BNZ` iteration in
    `verification/records/core-datapath/`), so the remaining work is firmware
    arithmetic, not an ISA question.
  - **Two further honest notes on the waveform.** (a) The first two run-phase
    cycles show TX **low**, before the program's first `OUT` drives the idle-high
    level; this is not a spurious start bit to any receiver, because a start bit
    is a 1→0 edge out of idle, and the program then holds the line idle-high for
    256 cycles (>5 bit periods) before the first real start bit. The independent
    decoder, searching for falling edges out of idle, skips it on its own — the
    bench does not mask it. (b) Captured transition timestamps carry a uniform
    +1 ps (one timescale step) offset from the clock edge, an artefact of
    sampling in cocotb's read-only phase; it is identical on every sample and
    therefore cancels exactly in every relative measurement (the 710-cycle frame
    pitch comes out as 14,200.000 ns, and drift as 0.000 ns).
