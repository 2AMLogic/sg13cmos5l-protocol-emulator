- **Record ID**: 20261010-020911-0f0490a
- **Claim**: DR 0013 layer 2, strap `01` (`spec/decision-records/0013-program-loading.md`, **Proposed, not ratified**), as issue #140 scopes it, holds on the RTL of the submitted top: **with `MODE` low and `ui_in[6:5] = 01`, the boot ROM's SPI-flash boot reads a 512-byte image from a Tiny Tapeout QSPI Pmod flash with one clean SPI mode 0 `0x03` transaction, and runs it only if it is a signed image; a blank, absent, zero or corrupt flash never reaches `RUN`, and the design drives only the Pmod's CS0, MOSI and SCK pins.** Specifically: (a) the flash is `verification/reference_models/spi_flash.py`, an independent behavioural model that answers `0x03` reads from a byte image and checks SPI mode 0 on every edge it sees (SCK idle low at CS edges and while CS is high, CS setup, hold and high time, MOSI setup and hold, SCK pulse widths, the READ frequency ceiling, MISO valid when clocked), fed only by the pins the design drives, resolved through the pad model with the Pmod's CS pull-ups (`uio[0]`, `uio[6]`, `uio[7]`); a good boot is exactly one transaction (opcode `0x03`, address 0, 512 bytes, 4,096 data clocks) with no violation, CS0 driven high by the design (not left to the pull-up) before the pins are released; (b) on every edge of the boot, the design's `uio_out` and `uio_oe` equal those of `BootModel` (the ISA interpreter of `test_boot_rom.py`, written from DR 0001/DR 0012, sharing no code with the RTL or the assembler) running the committed boot image against its own instance of the flash model, and `uo_out` stays 0; the same model gives the cycle count, 58,793 cycles from the boot program's first instruction to the image's first, independent of the image; (c) a signed image boots and its first instruction runs on the predicted edge with `R0`-`R3`, `Z`, `C` at reset values, `PM_ADDR` and `PM_CRC` 0, `BOOT_STATUS` 0 and every `uio` released, and two images with different filler boot to identical boot pin timing; (d) the committed `uart_tx` and `spi_mode0` programs, signed and placed in the flash, boot and are graded by `UartDecoder` (both frames, 50-cycle bit, drift bound) and `check_burst` (both bursts, 4- and 8-cycle SCLK) with their negative controls; (e) a blank (all `0xFF`) flash, no Pmod with MISO pulled high, no Pmod with MISO pulled low, a fitted flash of zeros, 7 images one defect from a good one (including residues with only one nonzero CRC byte), an image shifted by one byte, a truncated image, and a valid-CRC image with signature `0x0000` never run: the core never leaves the boot ROM (white-box, RTL), halts at `spi_fail`, and every `uio` is an input and `uo_out` 0 from the release edge on, even with a canary image in program memory; (f) over every run only `uio[0]`, `uio[1]` and `uio[3]` are ever driven, so the PSRAM chip selects `uio[6]`/`uio[7]` stay with the Pmod's pull-ups. **Findings recorded, see DR 0013's notes of issue #140:** F2, the PSRAM chip selects default to deselected (10 k pull-ups in the Pmod schematic, 1 k in its README, nothing measured); the boot refuses a signature of `0x0000` (the all-zero image is its own valid CRC, F1); the two boot programs now use 93 of the 128 ROM words, leaving 35 for the UART load (F3). **Not claimed:** (1) any real flash, Pmod, demo board or silicon: the pad model is logical and zero-delay; (2) the flash model's numeric limits are the W25Q128JV's as recalled by the author, not re-read from the datasheet; (3) anything on a gate-level netlist (that is `verification/records/firmware-gate-level/` at this commit, which runs this bench with `--boot-spi`); (4) a clock frequency, an area or a pad; (5) the UART-load boot (issue #139).
