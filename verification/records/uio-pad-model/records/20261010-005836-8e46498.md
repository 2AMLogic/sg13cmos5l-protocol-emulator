- **Record ID**: 20261010-005836-8e46498
- **Claim**: `verification/uio_pads.py` is a usable silicon-true `uio` pad model for the cocotb benches, as DR 0012 § Consequences and `spec/verification-plan.md` § 7 ("Silicon-true pad model") ask: per pin it resolves the design's `uio_oe`/`uio_out`, an optional pull and an optional external driver into one line, feeds that line back on `uio_in`, and detects contention. Three things are shown, on the tree that also carries #162's refactored bench parsers and #169's boot ROM. (1) *The rule*: `resolve_pin` matches a hand-written 36-case truth table, and contention is reported for known opposite drives and for nothing else, over all 144 combinations including unknown `uio_oe`. (2) *On the real top*: with small programs assembled in memory and loaded through the real load phase, input, push-pull (`UIO_DIR`) and open-drain (`UIO_OD`) pads behave at the line and through the core's own `IN` path as DR 0012's pin-mode rule says; a peripheral holding a released open-drain line low is not contention, including while the design toggles its pad under the hold; three real fights are each reported as one episode naming the pin and both levels. (3) *It sees what the old bus could not*: five defects in the top's `uio_oe` logic, none of which changes `uio_out` and so none of which could change the verdict of the bench-composed bus (`uio_out AND uio_in`), each make both directed I2C benches fail. The first of the five is the pre-DR-0012 top itself, `uio_oe = 8'h00`. **Why this record supersedes.** PR #169 (`1dc1842`; boot ROM, fetch-source switch and warm start, DR 0013 layer 2) changed `rtl/` and `src/` and merged to `main` while PR #163 (this branch, the pad model) was in review. `9cad200` is the merge of `main` into this branch and `c0c4d7e`, one commit later, adds the boot ROM source to `verification/request-uio-pads.json`; `c0c4d7e` is the tree this run is on, the first with both the boot ROM and a pad bench that elaborates. `20261009-222030-747aae3` hashes the top, the core and the program memory as they were before #169, and `verification/request-uio-pads.json` as it was before it listed the boot ROM. On the merged tree that request no longer elaborated, which is why `c0c4d7e` adds the one source line. Nothing else is corrected: the model, its bench, the unit tests and the mutant runner are unchanged, and all three parts were re-run. **What this record does not claim.** The pad model is zero-delay and logical: nothing here is evidence about pull-up rise time, pad propagation delay, drive strength or bus capacitance, and an I2C bus still needs external pull-ups this design does not provide. DR 0012 is **Proposed, not ratified**; this record makes no target-spec row met. The model's reset bookkeeping starts at reset *release*; `uio_oe == 0` while `rst_n` is low is `test_control_space.py`'s check, not this one's.
