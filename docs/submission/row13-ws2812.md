# Row 13: WS2812 on the frozen ISA

Status: **written 2026-10-10** for issue #134 (deliverable D6) from issue
#141 part 2. It describes evidence that is in the repository. It does not mark
target-spec row 13 met. The row is Proposed, unmet and outside DR 0004's
register, so the 2026-10-11 two-key act (PR #242), which ratified rows 1-12,
did not bind it. Its stretch column is the PS/2 device in
[`row13-ps2.md`](row13-ps2.md) (issue #235, closed 2026-10-11). Status claims
refreshed 2026-10-11 for issue #238.

## What was asked

The organizers' 2026-10-09 update made reprogrammability the main judging
criterion: "can the chip be reprogrammed to support protocols it wasn't
designed for?" Target-spec row 13 turns that into a test. Choose a protocol
**after** the instruction set is frozen, write it as firmware only, and grade it
with an independent reference model, timing included.

## How the order was kept honest

1. **Freeze.** DR 0017 pins the eleven files that define the ISA by sha256
   (`spec/isa-freeze.json`). Its PR merged as `1696045b`. From then on
   `scripts/check_isa_freeze.py` (`npm run lint`) fails on any change to those
   files that no recorded amendment covers.
2. **Choice.** DR 0018 chooses WS2812 in a commit whose parent is the freeze
   merge, before any WS2812 file existed. It checks the choice against DR 0017's
   exclusion list. It also searches the repository and its history: WS2812
   appears in three places, all added on 2026-10-09, and none of them weighs it
   against an instruction or a cycle budget.
3. **Build.** The program, model and bench came in later commits.
   No RTL, assembler or ISA-model byte changed, and this work added no freeze
   amendment. When this document was first written, the one amendment on `main` was #234's
   dated note in DR 0013, recorded as `no-behaviour-change`, with
   `invalidates_row13_evidence: false`. As of `main` @ `a9ac6940`
   (2026-10-11) `spec/isa-freeze.json` holds seven: six
   `no-behaviour-change` (DR 0013 for #234 and #211, DR 0001 for #85 and
   #44, and DR 0001 twice for PR #242's two-key act) and one
   `conformance-fix` (DR 0020's open-drain fix to the top, #244). All seven
   carry `invalidates_row13_evidence: false`.

| Gate-level evidence | [`firmware-ws2812-gate-level` 20261011-115014-e5a0bae](../../verification/records/firmware-ws2812-gate-level/records/20261011-115014-e5a0bae.md) (LibreLane netlist, zero-delay) |

The model measures every high and low pulse on `uo_out[7]`, classifies each
bit, checks each pulse against its datasheet window, splits frames at resets,
and rebuilds the GRB pixels. The bench compares those pixels with the table it
loaded: the committed frame, plus seeded random frames of 1 to 73 pixels (73
fills program memory). At RTL and on gates, every pulse in every run measured
the same:

| Pulse | Cycles | ns at 20 ns | WS2812B window | Margin to the nearer edge |
|---|---|---|---|---|
| T0H | 20 | 400 | 250–550 | 150 ns |
| T1H | 40 | 800 | 650–950 | 150 ns |
| T0L | 43 | 860 | 700–1000 | 140 ns |
| T1L | 23 | 460 | 300–600 | 140 ns |
| bit | 63 | 1260 | 650–1850 | 590 ns |
| reset | ≥ 15,499 | ≥ 309,980 | above 50,000 | — |

The ns column is cycles × 20 ns, which is target-spec row 4's target clock. That
clock is not yet confirmed, so these are cycle counts at a named clock, not
measured wall-clock times.

**It can fail.** Three mutant programs are rejected by the model, each for its
own reason. A T1H of 640 ns is rejected because the pulse fits neither code. A
dropped bit is rejected because the frame is 191 bits, not a whole number of
pixels. A 5.5 µs reset is rejected because the low is longer than any bit's low
but shorter than a reset. The golden capture stretched ×1.2 is also rejected.
On gates, with one bit of the WAIT counter stuck at 0, 5 of the 6 tests fail.

## What the frozen ISA made easy

- **Exact pulse widths from reading the program.** Every instruction takes 1
  cycle and `WAIT n` takes n + 1 (DR 0001). So each pulse width is a sum you can
  do by hand, and the assembler's cycle report does the same sum. On every bit
  of every run the measured widths equal that sum exactly, at RTL and on gates.
  WS2812 has no clock line and no handshake, so this guarantee is the whole
  job.
- **No branch on the bit value.** A bit is three writes:
  `OUT 0x80` (rise), then 20 cycles later `OUT (byte AND 0x80)`, then 20
  cycles after that `OUT 0`. The bit's value only decides which of two fixed
  instants the line falls at. No instruction's latency depends on data
  (target-spec row 3), and nothing in a frame branches on pixel data.
- **One constant does two jobs.** With DIN on bit 7, `0x80` is both the
  line-high pin image and the mask for the next bit out (WS2812 sends the most
  significant bit first).
- **Generous WAIT range.** Each bit uses three `WAIT`s (16, 18 and 18 cycles,
  or 12 on a byte boundary). The 310 µs reset is a constant-count loop of
  `WAIT 255` × 60 at 258 cycles per pass. Everything fits the 8-bit immediate,
  with room to retune for a different clock.
- **Program memory as a frame buffer.** DR 0012's `PM_DATA_HI`/`PM_DATA_LO`
  reads (fixed 2 + 1 cycles) let the pixels live in a table after the code. A
  host can load a different frame without touching a code word, which is what
  the random-frame tests do. The fetch fits in the 23-cycle low phase of each
  byte's last bit.

## What it made hard

- **Four registers, all used.** The byte being sent, a scratch register, the
  `0x80` constant and the bit counter use all four. No register is left to count
  bytes, so the frame ends at a marker in the table, not at a count.
- **No readable carry, no immediate ALU ops.** `SHF` moves the outgoing bit
  into `C`, but no instruction reads `C` (DR 0016), so the bit test is
  `MOV` + `AND` with the constant register. `SHF` also leaves `Z` alone, so the
  bit counter (a 1 shifted left eight times) needs an extra `OR R3, R3` before
  the branch. That costs nothing at a 20-cycle budget. It would matter for a
  faster protocol.
- **Balancing paths by hand.** There is no call or return, so the next-byte
  fetch is inline in the 8th bit's tail. That path and the mid-byte path must
  both be exactly 63 cycles, and the padding was worked out by hand. The
  assembler's `.cyclesec` report and the bench check it (bit loop 63; byte path
  44 + 19 = 63).
- **No data directive.** The assembler (pinned by the freeze) has no `.word`.
  So the table is written as `LDI R0, b` instructions that never run. That is
  one byte per 16-bit word, and the high byte (`0x10`) serves as the
  "more data" flag. Packing two bytes per word would need a fifth register.
  The cost is 73 pixels, not about 146.
- **A lint false positive.** The assembler's data-dependence lint treats every
  `PM_DATA` read as possibly pin-derived. So it warns on the two end-of-table
  branches, which are not timing loops. The bench pins exactly those two
  warnings, and the program header explains them.
- **The load-phase readout shares the pin.** During a serial load, every
  `uo_out` pin shows the running `PM_CRC` (DR 0013 layer 1). A strip on
  `uo_out[7]` therefore sees CRC bits until `MODE` drops. The program opens
  with a 310 µs reset, so the first frame a strip latches is the right one. A
  strip may still flash during the load.

## What this does not show

- **No SDF or pad timing.** The gate-level run is zero-delay. Pad slew and
  output delay at a real pin are not simulated, and
  `flow/run-post-layout-sdf.sh` runs the core bench and, with
  `--suite protocols`, the UART TX, SPI and I2C repeated-START benches
  (record `20261011-114800-e5a0bae`), but not this one. A pulse's width at
  the pin moves by the difference between the pin's rise and fall delays.
  That difference has not been measured for this program, so the 140 ns
  margin is a margin on the simulated waveform, not at the pin.
- **Clock.** Every ns figure assumes the 50 MHz target. At another clock, the
  `WAIT` immediates must be recomputed.
- **No board.** Nothing here ran on silicon or an FPGA.
- **The stretch** (a new role or pin direction) is the PS/2 device in
  [`row13-ps2.md`](row13-ps2.md); issue #235 is closed.
